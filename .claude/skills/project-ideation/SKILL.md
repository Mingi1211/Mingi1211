# project-ideation — 학교 프로젝트 주제 선정·검증

2026-09 광운대 팀 프로젝트 주제 선정에서 **4번의 반려를 거쳐** 얻은 방법론.
핵심 교훈: **좋은 아이디어를 찾는 것보다, 나쁜 아이디어를 빨리 죽이는 게 중요하다.**

## 1단계 — 킬 필터 (아이디어를 내기 전에 먼저 읽을 것)

아래 중 **하나라도 걸리면 그 주제는 버린다.** 살려보려 하지 말 것. 실제로 4개가 여기서 죽었다.

| # | 필터 | 왜 치명적인가 | 실제 사망 사례 |
|---|---|---|---|
| 1 | **외부 기관의 협조·권한·데이터 제공이 필요한가** | "학교가 DB 안 주면요?" 한 문장에 무너짐 | 캠퍼스 공간·장비 통합 예약 |
| 2 | **공식 시스템이 이미 제공하는 기능인가** | "그거 포털에 있는데요?" | 졸업요건 자가진단 (KLAS에 졸업심사 존재) |
| 3 | **틀리면 사용자에게 돌이킬 수 없는 피해를 주는가** | 졸업·법률·의료는 학생 프로젝트가 감당 못 함 | 졸업요건, 자취방 계약 체크 |
| 4 | **개인정보 수집·동의 절차가 필요한가** | 프로토타입 단계에서 과도한 설계 | 개인 일정 캘린더 연동 |
| 5 | **전공 심화가 과한가** (일부 전공만 참여 가능) | 팀 프로젝트 과목의 취지와 불일치 | 자연어 로봇 동작 시뮬레이터 |
| 6 | **기존 범용 서비스와 정면 충돌하는가** | "when2meet 있는데요?" | 팀플 시간표 매칭 |
| 7 | **사용자가 0명이면 작동을 안 하는가** (콜드스타트) | 발표 데모가 성립 안 됨 | 매칭·중고거래류 대부분 |

## 2단계 — 살아남은 주제의 데이터 출처 확인

**데이터를 누가 소유하는가**가 주제의 생사를 가른다. 셋 중 하나여야 한다.

1. **팀이 직접 수집** — A팀이 메뉴판을 직접 촬영한 구조. 가장 강하다.
   발표에서 "데이터 어떻게 모았나요?"에 **"저희가 직접 했습니다"**로 답할 수 있다
2. **사용자가 직접 입력** — 권한 문제를 구조적으로 제거한다
3. **공개 자료를 팀이 옮겨 적음** — 크롤링이 아니라 전사(轉寫). 부하도 안 주고 시비도 없다

> **팀원 본인의 경험이 곧 1차 데이터가 되는 주제**가 최고다.
> 8명 × 각자 아는 것 = 즉시 확보되는 데이터셋. 외부 협조 0.

## 3단계 — 차별점은 "더 좋게"가 아니라 "축이 다르게"

기존 서비스보다 잘 만들겠다는 건 차별점이 아니다. **무엇을 보는지가 달라야** 한다.

```
에브리타임 시간표 마법사  →  요일·시간 축
학기예보                 →  학기 16주 축          ← 축이 다르다
```

기존 도구 표를 만들고 `무엇을 하는가 / 무엇을 못 하는가` 두 칸을 채워라.
**"못 하는 것" 칸이 우리 제품의 정의다.**

## 4단계 — 데이터가 부정확할 수밖에 없을 때

정확도를 주장하면 진다. 제품의 정의를 바꿔서 불확실성을 **전제로 흡수**한다.

| 기법 | 내용 | 사례 |
|---|---|---|
| **은유 교체** | "판정" → "예보". 예보는 원래 확률이므로 틀려도 제품이 안 무너진다 | 학기 난이도 |
| **안정적 신호만 사용** | 잘 안 변하는 속성(형태·시점)만 쓰고 휘발성 높은 것(개수·난도)은 버린다 | 과목 부담 |
| **집계 단위 상향** | 개별 정확도 대신 **조합의 구조적 위험**을 판다. "프로젝트형 3과목 동시는 위험"은 누가 가르쳐도 참 | 조합 경고 |
| **신뢰도 등급 노출** | A/B/C를 화면에 그대로 표시. "모른다"고 말하는 게 틀린 숫자보다 강하다 | 과목 데이터 |
| **소급 검증** | 과거 사례로 예측하고 실제와 대조해 정확도를 **주장이 아니라 측정**으로 만든다 | 지난 학기 수강생 15명 |

## 5단계 — 공격 질문 방어 시트 (필수 산출물)

사용자가 가장 중요하게 보는 항목. **주제안 문서에 표로 넣는다.** 자주 나오는 10개:

1. 학교/기관 권한은 받았나요
2. 이미 있는 기능/서비스 아닌가요
3. 데이터가 틀리면 책임은
4. 개인정보 문제는
5. 유지보수는 (매년 바뀌는데)
6. 범위가 너무 넓지 않나요
7. 대기업/전국 서비스가 하면 끝 아닌가요
8. 기술적으로 너무 쉬운 것 아닌가요
9. 사용자가 없으면 무용지물 아닌가요
10. 왜 하필 우리 학교만

> **8번 대응이 특히 중요.** 난도를 코드 복잡도가 아니라
> **"도메인 모델링의 정확도"**로 재정의하고, 성과 지표도 코드량이 아닌
> **커버리지(N개)와 정확도(N%)**로 잡는다.

## 6단계 — 재미·트렌드 요소를 넣을 때

사용자는 재미를 중시하되 **기능과 붙어 있을 때만** 인정한다.

- ❌ 캐릭터가 결과 옆에 서 있다 (장식)
- ✅ 캐릭터가 팔을 내리는 동작이 **그대로 "이 과목 빼세요" 추천을 가리킨다** (기능)

**정당화 논리**: 공유 → 유입 → 데이터 입력 증가 → 제품 정확도 상승.
재미가 품질에 직결되는 선순환을 그릴 수 있으면 "본질이 아니다"는 공격이 막힌다.

**IP 안전판**: 실존 인물·영상·음원·특정 안무를 착안은 해도 **사용하지 않는다.**
자체 캐릭터의 일반적 동작으로만 구현하고, 발표 자료에도 실존 인물 이미지를 넣지 않는다.
학교 마스코트는 **2차 가공 승인 절차가 있는 경우가 많다** → 의존하지 말고 "승인 시 추가되는 선택 스킨"으로 설계.

## 산출물 템플릿

Project Charter 8항목(팀/배경·목적/결과물·목표/범위/일정/R&R/리스크·제약/그라운드룰)에 더해 항상 포함:

- **범위 밖 (명시적으로 안 하는 것)** — 이게 없으면 한 학기에 못 끝낸다
- **공격 질문 방어 시트**
- **탈락 대안 기록** — "왜 이걸 골랐나"의 근거
- **측정 가능한 목표** — 커버리지 N개, 정확도 N%, 사용자 테스트 N명
- **중간 게이트** — "N월 N주까지 X가 안 되면 Y안으로 전환"을 헌장에 명시

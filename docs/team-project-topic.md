# 팀 프로젝트 주제안 — `학기예보`

> 수강 조합의 학기 중 부담 분포를 예보하는 서비스
>
> 팀 구성: 8명 (로봇학부 + 소프트웨어 + 전자) · 하드웨어 설계 없음 · 웹 서비스
> 참고: A팀(장박사) "월계동 맛집 추천 웹서비스" 회의록 / Project Charter 양식 PPT

## 1. 문제 정의 (Why)

### 한 문장 문제 정의
> **수강신청은 "요일과 시간"으로만 짜는데, 학기를 실제로 망가뜨리는 것은 "10주차에 몰린 부담"이다.**

### 왜 지금 수단으로는 안 되는가

| 기존 수단 | 무엇을 하는가 | 무엇을 못 하는가 |
|---|---|---|
| **에브리타임 시간표 마법사** | 시간이 겹치지 않는 **모든 조합**을 자동 생성 | 요일·시간 축만 본다. 학기 중 어느 시점에 부담이 몰리는지는 전혀 고려하지 않음 |
| **에브리타임 강의평** | 과목별 후기 텍스트 | 사람마다 기준이 다르고, 무엇보다 **"이 6과목을 같이 들으면 어떻게 되는가"** 는 아무도 안 알려줌 |
| **강의계획서** | 평가비중·주차별 계획(공식) | 과목별로 흩어져 있어 조합해서 볼 수 없음 |

**공백: 조합 단위로, 시간축이 아니라 학기축으로 부담을 보여주는 도구가 없다.**

### 타깃 사용자 (좁히는 것이 이 아이디어의 강점)

이 서비스는 "쉬운 시간표"를 원하는 사람을 위한 것이 **아니다**.
**학기 외에 반드시 지켜야 할 일정이 있는 사람**을 위한 것이다.

| 대상 | 지켜야 할 일정 | 필요한 것 |
|---|---|---|
| 취업 준비 고학년 | 하반기 공채 자소서(9~10월), 면접(11월) | 그 시기에 전공 부담이 겹치지 않는 조합 |
| 학부연구생 | 매주 랩미팅, 논문·실험 | 상시 과제형 과목이 누적되지 않는 조합 |
| 대외활동·공모전 병행 2학년 이상 | 공모전 마감, 프로젝트 데모 | 프로젝트형 과목 중복 회피 |

## 2. 핵심 설계 판단 ⚠️ — 데이터 불확실성을 어떻게 다루는가

### 지적된 문제
> "같은 수업이라도 교수님이 다음 학기에 운영을 달리할 수 있고, 과제를 언제 얼마나 내주는지·시험 난도와 횟수는 직접 들은 사람 아니면 알기 힘들다."

**이 지적은 옳다. 그래서 제품의 정의 자체를 바꾼다.**

### 개선 1 — "난이도 판정"이 아니라 "부담 예보"

절대 난이도(이 과목은 5점 만점에 4점)를 주장하는 순간 반박당한다.
서비스의 은유를 **일기예보**로 잡는다.

> **예보는 원래 확률이다.** 우리는 정답을 말하지 않고, 확률과 신뢰도를 함께 제시한다.
> 사용자도 "강수확률 60%"를 정답으로 받아들이지 않으면서 우산은 챙긴다.

이 프레이밍 하나로 데이터 불확실성이 **결함에서 전제로** 바뀐다. 서비스명을 `학기예보`로 잡은 이유다.

### 개선 2 — 교수가 바뀌어도 살아남는 신호만 쓴다

정확도가 떨어지는 신호(과제 개수, 시험 난도)에 기대지 않고, **과목 성격에 붙어 있어 잘 안 변하는 신호**를 1차 근거로 삼는다.

| 쓰는 신호 (안정적) | 안 쓰는 신호 (휘발적) |
|---|---|
| **부담의 형태** — 시험형 / 과제형 / 프로젝트형 / 출석형 | 과제 정확한 개수 |
| **부담의 시점** — 중간·기말 집중형 vs 상시 누적형 | 시험 문항 난도 |
| **평가비중** (강의계획서 공식 기재) | 교수 개인의 채점 성향 |
| **조합 충돌** — 같은 형태의 부담이 겹치는가 | 학점 잘 주는지 여부 |

**핵심 논리: 개별 과목 정보가 다소 부정확해도 "프로젝트형 3과목 동시 수강은 위험하다"는 결론은 교수가 누구든 성립한다.**
→ 우리가 파는 것은 개별 과목의 정답이 아니라 **조합의 구조적 위험**이다. 이 구분이 이 프로젝트 전체를 지탱한다.

### 개선 3 — 데이터 단위를 `과목 × 교수 × 학기`로

과목명 하나에 데이터를 묶으면 교수 교체 시 전부 오염된다. 키를 셋으로 쪼갠다.
- 담당교수가 바뀌면 이전 학기 데이터는 자동으로 **"참고(신뢰도 강등)"** 로 표시
- 화면에 **"2025-2학기 · ○○○ 교수 기준"** 을 항상 병기

### 개선 4 — 신뢰도 등급을 숨기지 않고 전면에 표시

| 등급 | 조건 | 화면 표기 |
|---|---|---|
| **A** | 강의계획서 + 수강 경험자 3명 이상 검증 | 초록 · "검증됨" |
| **B** | 강의계획서만 | 노랑 · "공식 자료 기반" |
| **C** | 담당교수 변경 / 데이터 부족 / 유사 과목 추정 | 회색 · **"정보 부족 — 참고만"** |

> "이 과목은 정보가 부족합니다"라고 정직하게 말하는 것이, 틀린 숫자를 자신 있게 보여주는 것보다 훨씬 강하다.
> 발표에서 "교수가 바뀌면요?"라는 질문에 대한 답이 **이미 화면 안에 들어 있다.**

### 개선 5 — 개인 일정을 먼저 받는다

과목 부담을 단독으로 평가하지 않고, **사용자의 학기 외 일정 위에 겹쳐 그린다.**

```
[내 일정]  9월 자소서 ███  10월 자소서 ███  11월 면접 ████
[수강부담]         ██     ████████ ← 10주차 충돌 경보
```

이러면 데이터가 완벽하지 않아도 가치가 성립한다. 우리가 제공하는 것은
"이 과목이 어렵다"가 아니라 **"당신이 바쁜 그 시기에 부담이 겹칠 가능성이 높다"** 는 경고이기 때문이다.

## 3. 무엇을 만드는가 (What)

### 한 줄 정의
> **시간표 마법사가 요일·시간의 빈칸을 채운다면, `학기예보`는 학기 중 에너지의 빈칸을 본다.**

### MVP 기능 (반드시 구현)

1. **내 일정 입력** — 취준 / 학부연구생 / 공모전 프리셋 + 직접 입력 → 학기 16주 타임라인에 "내가 바쁜 시기" 표시
2. **과목 담기** — 개설 과목에서 후보 조합 구성 (여러 조합 저장·비교)
3. **주차별 부담 히트맵** ★ — 과목별 부담을 주차에 배분해 누적 표시. 내 일정과 겹치는 구간을 강조
4. **조합 경고** — 절대치가 아닌 구조적 위험을 문장으로 제시
   - "프로젝트형 3과목 동시 — 11~14주 과부하 위험"
   - "기말 100% 반영 과목 2개 — 학기 말 집중"
   - "상시 과제형 4과목 — 매주 누적 부담"
5. **대안 제시** — 같은 이수구분 안에서 **부담 형태가 다른** 대체 과목 추천
6. **신뢰도·근거 표시** — 과목마다 A/B/C 등급 + 기준 학기 + 담당교수 + 데이터 출처
7. **학기 회고 30초** — 학기 말에 자기가 들은 과목 부담을 입력하면 다음 학기 예보 정확도가 올라감 (데이터 축적 루프)

### 확장 기능 (여유 시)
8. **최소 부담 조합 탐색** — 목표 학점과 내 일정을 주면 부담이 가장 고르게 분산되는 조합을 자동 탐색 (시간표 마법사에 대응하는 우리 버전)
9. 조합 공유 링크 — 선배·동기와 시간표 상담
10. 학부·전공별 "이 시기에 다들 바쁘다" 집계 보기

### 범위 밖 (명시적으로 안 함) ⚠️
- **교수 개인에 대한 평가·랭킹·점수화** — 과목의 *성격*만 다루고 사람을 평가하지 않는다. 명예훼손 및 윤리 문제를 원천 차단
- 성적(학점) 예측 — "이 조합이면 4.0" 같은 주장은 하지 않는다
- 수강신청 대행·매크로 등 학사 시스템 개입
- 학교 DB 연동, 계정 연동, 크롤링
- 하드웨어·회로·기구 설계

## 4. 데이터를 어떻게 확보하는가 (가장 중요)

### 3단 구조

| 단계 | 출처 | 담당 | 커버리지 |
|---|---|---|---|
| **1차 — 팀 내부 경험** | **팀원 8명이 이미 수강한 과목** | 전원 | 1인당 20~30과목 → 중복 제외 **80과목 이상** |
| **2차 — 공식 문서** | 강의계획서의 평가비중·주차별 계획 | 조사 담당 2명 | 개설 전공과목 전반 |
| **3차 — 선배 설문** | 구글폼 (학부 단톡방·학회 배포) | 기획 담당 | 목표 응답 50명 |

> **1차가 핵심이다.** 8명이 이미 들은 과목만으로 서비스가 즉시 작동한다.
> 외부 협조가 0이고, A팀이 메뉴판을 직접 촬영한 것과 정확히 같은 구조다.
> 발표에서 "데이터는 어떻게 모았나요?"에 **"저희가 직접 들은 과목부터 시작했습니다"** 라고 답할 수 있다.

### 수집 항목 (설문·엑셀 칼럼 확정안)
`순번 / 학부 / 과목명 / 학수번호 / 담당교수 / 수강학기 / 이수구분 / 학점 / 평가비중(중간·기말·과제·출석·기타) / 부담형태(시험형·과제형·프로젝트형·출석형) / 과제 주기(매주·격주·비정기·없음) / 팀프로젝트 유무 / 발표 유무 / 시험 횟수 / 부담 집중 주차(복수 선택) / 체감 부담(1~5) / 응답자 유형(팀원·선배) / 신뢰도 등급 / 최종 확인일`

## 5. 목표 (측정 가능하게)

- 3개 학부 전공과목 **80과목** 부담 프로파일 구축, 그중 **40과목 이상 A등급**
- 선배 설문 **응답 50명** 확보
- **소급 검증** ★ — 지난 학기를 실제로 수강한 **15명**에게 "그 학기에 힘들었던 주차"를 묻고, 우리 히트맵과 대조해 **70% 이상 일치**
- 사용자 테스트 **2학년 이상 20명**, "다음 수강신청에 쓰겠다" **70% 이상**
- 최종 발표에서 **현장 즉석 조합 입력 데모 성공**

> 소급 검증은 이 프로젝트의 승부수다. "예보가 맞는가"를 **과거 학기로 실제 측정**하면, 데이터 불확실성 공격에 숫자로 답할 수 있다.

## 6. 예상 공격 질문 & 방어 ⭐

| # | 예상 질문 | 답변 |
|---|---|---|
| 1 | **교수님이 바뀌면 데이터가 무용지물 아닌가요?** | 데이터를 `과목 × 교수 × 학기`로 관리하고, 교수가 바뀌면 신뢰도를 자동 강등해 화면에 표시합니다. 또한 저희가 쓰는 주 신호는 과제 개수가 아니라 **교수가 바뀌어도 잘 안 변하는 과목의 부담 형태**입니다 |
| 2 | **직접 들은 사람 아니면 모르는 정보 아닌가요?** | 맞습니다. 그래서 **저희 팀 8명이 이미 들은 과목**을 1차 데이터로 삼고, 모르는 과목은 "정보 부족(C)"이라고 표시합니다. 모르는 것을 아는 척하지 않는 것이 설계 원칙입니다 |
| 3 | **에브리타임 시간표 마법사와 뭐가 다른가요?** | 마법사는 **요일·시간**이 겹치지 않는 조합을 만듭니다. 저희는 **학기 16주 중 부담이 언제 몰리는지**를 봅니다. 축이 다릅니다 |
| 4 | **강의평이랑 뭐가 다른가요?** | 강의평은 과목 하나하나의 후기입니다. 저희는 **조합**을 봅니다. "이 6과목을 같이 들으면"에 답하는 건 아무도 안 합니다 |
| 5 | **예측이 틀리면요?** | 저희는 판정이 아니라 **예보**를 합니다. 신뢰도 등급과 근거를 항상 함께 표시하고, 지난 학기 수강생 15명과 소급 대조해 정확도를 수치로 공개합니다 |
| 6 | **교수님 평가 서비스 아닌가요?** | 아닙니다. 교수 개인에 대한 점수·랭킹은 **기능 범위에서 명시적으로 제외**했습니다. 과목의 성격만 다룹니다 |
| 7 | **학교 데이터 권한이 필요하지 않나요?** | 필요 없습니다. 팀 경험 + 공개 강의계획서 + 자발적 설문만 사용하며 학교 시스템과 통신하지 않습니다 |
| 8 | **사용자가 없으면 작동 안 하지 않나요?** | 팀이 미리 채운 80과목으로 첫날부터 작동합니다. 사용자 제보는 정확도를 올리는 보조 수단입니다 |
| 9 | **기술적으로 쉬운 것 아닌가요?** | 난도의 핵심은 **부담을 주차 단위로 모델링하고 조합의 위험을 탐지하는 규칙 설계**, 그리고 8번 확장 기능의 **조합 탐색 알고리즘**입니다 |
| 10 | **왜 광운대만 하나요?** | 학교마다 커리큘럼과 과목이 달라 **한 학교를 깊게 파는 쪽이 유리한 구조**입니다. 전국 서비스가 못 하는 정확도가 저희 차별점입니다 |

## 7. 기술 스택 (전부 무료 / 저비용)

- 프론트: React + TypeScript + Vite, 반응형
- 시각화: 주차별 부담 히트맵·타임라인 (경량 차트 라이브러리 또는 자체 SVG)
- **부담 모델링 엔진**: 평가비중·부담형태를 16주 타임라인에 배분하고 조합 위험을 탐지하는 자체 모듈 (본 프로젝트의 핵심)
- 백엔드: FastAPI 또는 Next.js API Route
- DB: PostgreSQL (Supabase 무료 티어)
- 설문: Google Forms → CSV → DB 이관
- 배포: Vercel 무료 티어
- 개발 도구: Cursor, Claude Code / 협업: GitHub, Notion, Figma

## 13. 최종 발표 데모 시나리오 (5분)

1. 문제 제기 — 시간표 마법사 화면 한 장. **"이 도구는 요일과 시간만 봅니다. 그런데 학기를 망치는 건 10주차입니다"**
2. 내 일정 입력 → **"10월 자소서, 11월 면접"** 프리셋 선택
3. 과목 6개 담기 → **주차별 부담 히트맵**이 그려지는 장면
4. 빨간 경고: **"프로젝트형 3과목 동시 — 11~14주 과부하, 면접 기간과 충돌"**
5. 대안 제시 → 한 과목 교체 → 히트맵이 평탄해지는 **before/after 비교**
6. 신뢰도 표시 클로즈업 — "이 과목은 정보 부족(C)입니다" 화면을 **일부러 보여주며** 정직성 강조
7. 성과 정리 — 80과목 커버리지, **소급 검증 15명 대조 정확도**, 사용자 테스트 20명 결과
